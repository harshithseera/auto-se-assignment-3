# ADR-006: Model choice per role (D6)

## Status

Accepted (2026-11-21)

## Context

Each role can use a different model, trading off capability, cost and speed. A different reviewer model is allowed but not required; using the same model for implementer and reviewer risks shared blind spots. A hard spending limit must be set before the first run and total tokens reported.

Options available:

- Same model for all roles
- Stronger model for implementation, cheaper for requirements/design
- Different model (or provider) for the reviewer

## Decision

We will use **Claude Sonnet (`claude-sonnet-5-5`)** for both the builder and the reviewer. It runs through Claude Code on the team's **Claude Pro** subscription, authenticated in Actions with a long-lived OAuth token from `claude setup-token`, stored as the repository secret `CLAUDE_CODE_OAUTH_TOKEN`.

We have no API credits and one day to build, so we need the option that is most certain to work. Pro already includes Claude Code, and Sonnet is the model it provides reliably. A different model for the reviewer is optional in the assignment, and getting it would mean paying for API access. The reviewer's independence comes from its job, prompt, inputs and permissions instead (ADR-008).

The spending cap is the flat subscription fee. No pay-as-you-go API billing is turned on, so a runaway run cannot add charges. Token use is read from `claude -p --output-format json` for every stage and reported in `results/results.csv`.

## Consequences

- No surprise cost, and only one secret to manage.
- Builder and reviewer share the same blind spots. A mistake Sonnet tends to make when writing code may also be one it misses when reviewing. The seeded-PR experiment measures this.
- Pro request limits restrict how many full runs fit in a day. A run that hits the limit fails partway, which looks like a stuck stage. ADR-009 handles it with timeouts.
- If the subscription token expires or is revoked, every run fails at its first agent call.
