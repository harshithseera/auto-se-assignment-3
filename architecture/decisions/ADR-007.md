# ADR-007: How stage checks are performed (D7)

## Status

Accepted (2026-11-21)

## Context

The checks are fixed: acceptance criteria are testable; the design names files and functions; the code builds; all new and existing tests pass; the PR is open and CI passes; the reviewer approves or two rounds are used. An agent judging its own output is unreliable. PRs opened with `GITHUB_TOKEN` do not trigger `on: pull_request` workflows, so CI must be invoked another way.

Options available:

- Deterministic checks in code (scripts, pytest exit codes, grep, gh)
- LLM-as-judge
- A mix: deterministic where possible, LLM judge only where no script can decide

## Decision

We will make every check deterministic: Python code in the pipeline decides each pass or fail, and no LLM judges any result.

| Stage | Check (in code) |
|---|---|
| 1 Requirements | `spec.md` has an `## Acceptance criteria` section with at least one line matching `AC-<n>: Given … When … Then …`, and an empty `## Blocking open questions` section. |
| 2 Design | `design.md` lists at least one existing file under `## Files to change`, and every `path::name` under `## Functions` can be found with `grep` in that file. New files are allowed only under `tests/`. |
| 3 Implementation | The diff is not empty, does not touch `.github/`, and both `python -m compileall -q tinydb` and `python -c "import tinydb"` succeed. |
| 4 Testing | Every `AC-<n>` has a test whose name contains `ac<n>`, and `python -m pytest` exits 0 on the full suite. The **script** writes `test_report.md` from pytest's output. |
| 5 Release | `gh pr view` reports the PR as `OPEN`, and the `ci` job (reusable `ci.yml` running pytest) succeeds. |
| 6 Review | The script reads `VERDICT: approve`, `changes-code` or `changes-approach` from `review.md`. A missing or malformed verdict stops the run. It does not count as approval. |

We chose deterministic checks because we want reliable results, and because an agent grading its own output is the least trustworthy check available. Stage 5 calls CI as a reusable workflow because PRs opened with `GITHUB_TOKEN` do not trigger `on: pull_request` workflows.

## Consequences

- Every pass or fail can be repeated and explained from the log.
- These checks test form, not meaning. A criterion can be in Given/When/Then form and still be vague. A test named `test_ac1_...` can be trivial. The independent reviewer and the hidden acceptance tests are what catch these. That gap is expected and reported in Results.
- The format rules have to be written into the stage prompts, or the checks will fail on correct work written in another format.
- A vague issue fails stage 1 by design, because its open questions block testable criteria. That counts as a correct stop, not a pipeline failure.
