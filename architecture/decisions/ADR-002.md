# ADR-002: Control flow between stages (D2)

## Status

Accepted (2026-11-21)

## Context

Stages run in order, but test failures return to implementation, repeated failures may force a return to design, and review feedback returns to design (approach issues) or implementation (code issues) for at most two review rounds. GitHub Actions jobs form a static graph decided before the run starts, and comments or pushes made with `GITHUB_TOKEN` do not trigger new workflow runs, so a workflow cannot easily re-invoke itself.

Options available:

- Fixed pipeline in a script, with loops written in code
- Orchestrator agent that decides the next stage
- Explicit state machine (e.g. LangGraph)
- Chained Actions jobs only, with the review loop unrolled as conditional jobs

## Decision

We will drive stages 1–5 with a fixed Python pipeline (`pipeline.py`) inside one `build` job. All loops and send-backs are written in code:

- Implement → test runs at most 3 times. If tests still fail, the pipeline goes back to design once and tries implement → test 3 more times. Then it stops.
- If any check fails beyond its budget, the stage writes the reason into its artifact and the run stops.

The review loop is written out as fixed Actions jobs with `if:` conditions: `build → ci → review-1 → fix-1 → ci-2 → review-2`. `fix-1` runs only if review 1 asks for changes. It re-enters the pipeline at stage 2 when the verdict is `changes-approach` and at stage 3 when it is `changes-code`. Review 2 is final. That gives at most two review rounds.

We chose this over an orchestrator agent because we want reliable runs. A script cannot skip a check, invent a new stage, or loop until the budget runs out, and every send-back can be read in code. We need the review loop as fixed jobs because comments and pushes made with `GITHUB_TOKEN` do not start new workflow runs, so the workflow cannot re-trigger itself.

## Consequences

- Control flow is predictable and readable. The maximum number of agent calls in a run is fixed and can be worked out from the code and the YAML.
- The pipeline cannot adapt. It cannot decide to add more tests or come back to a stage outside the fixed rules.
- More review rounds would mean editing the YAML. The `fix`, `ci` and `review` jobs are partly duplicated.
- Each job starts on a fresh runner, so state has to be carried between jobs (see ADR-004).
- Every extra job adds setup time: checkout, Python install, Claude Code install.
